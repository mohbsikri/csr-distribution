# /human-validation

## Purpose

Record human answers, evidence, decisions, and confirmations for questions generated by `/generate-questions`.

This command implements Step 5 — Human Validation of the CSR pipeline.

It applies the **Question-Centric Validation Model**: questions are the primary validation entities and persist independently of the sessions in which they receive input. Validation Sessions are supporting traceability structures that record the context, actors, and decisions of each discrete validation interaction.

Human Validation is mandatory. No question may be automatically closed. Evidence may inform or suggest an answer, but human confirmation is required to transition any question to ANSWERED or VALIDATED status.

---

## Inputs

The command reads:

### Canonical Question Records

```text
workspaces/<workspace_id>/knowledge_base/questions/questions_report.md
```

Fields consumed from each question record:

| Field | Used for |
| ----- | -------- |
| `question_id` | Question identity and session traceability |
| `conflict_id` | Upstream conflict traceability link |
| `Conflict Type` | Answer format requirements |
| `Severity` | Validation priority — BLOCKING questions must be addressed before consolidation |
| `Status` | Processing filter — eligible statuses: UNANSWERED, PARTIALLY_ANSWERED, REJECTED (see status normalization note below) |
| `Question` | Human review — the question being answered |
| `Context` | Human review — source, section, content, and reason from the originating conflict |

### Status Normalization

The upstream command `/generate-questions` writes status values in lowercase (`unanswered`, `answered`, `resolved`).

`/human-validation` treats status values as **case-insensitive** when reading from the canonical question records.

When `/human-validation` writes or updates a status value, it writes in **UPPERCASE**.

This establishes UPPERCASE as the canonical status format from this stage forward. The lowercase `unanswered` initial state written by `/generate-questions` is treated as equivalent to `UNANSWERED` for all processing and filtering purposes.

### Human-Readable Review Artifact

```text
workspaces/<workspace_id>/output/generated_questions/questions_for_review.md
```

Used for human review context. This file is not modified by this command.

---

## Outputs

### Validation Session Records

```text
workspaces/<workspace_id>/input/validations/<session_id>.md
```

One file per validation session. Each session record captures all activity from a single validation interaction: participants, questions addressed, evidence cited, decisions made.

### Updated Canonical Question Records

```text
workspaces/<workspace_id>/knowledge_base/questions/questions_report.md
```

For each question addressed in the session, the canonical record is updated in place:

- `Status` field is updated to reflect the new lifecycle state.
- Answer fields are appended to the existing record structure.
- Original question fields (question_id, conflict_id, type, severity, question text, context) are preserved unchanged.

---

## Question Lifecycle

Questions follow a defined lifecycle managed across one or more validation sessions.

| Status | Description | Managed By |
| ------ | ----------- | ---------- |
| `UNANSWERED` | No answer recorded. Initial state set by `/generate-questions`. | `/generate-questions` |
| `PARTIALLY_ANSWERED` | Answer recording has begun but required fields are incomplete or the answer was explicitly recorded as partial. | `/human-validation` |
| `ANSWERED` | A complete human answer has been recorded. Not yet confirmed by a designated validator. | `/human-validation` |
| `VALIDATED` | A human validator has explicitly confirmed the answer as complete and correct. This is the terminal state for active questions. | `/human-validation` |
| `REJECTED` | A reviewer has found the answer insufficient. The question must be re-answered. The rejected answer is preserved for reference. | `/human-validation` |
| `SUPERSEDED` | A previously VALIDATED answer has been replaced by a newer VALIDATED answer. The original answer is preserved. SUPERSEDED is not REJECTED. | `/human-validation` |
| `RESOLVED` | The validated answer has been incorporated by `/consolidate-knowledge`. | `/consolidate-knowledge` |

`/human-validation` manages all transitions from `UNANSWERED` through `SUPERSEDED`.

`/consolidate-knowledge` manages the `RESOLVED` transition and does not set status prior to that.

### Valid Lifecycle Transitions

| From | To | Trigger |
| ---- | -- | ------- |
| `UNANSWERED` | `PARTIALLY_ANSWERED` | Answer recording begins; answer is incomplete |
| `UNANSWERED` | `ANSWERED` | Complete answer recorded in a single session |
| `PARTIALLY_ANSWERED` | `PARTIALLY_ANSWERED` | Additional input provided; still incomplete |
| `PARTIALLY_ANSWERED` | `ANSWERED` | Remaining required fields completed |
| `ANSWERED` | `VALIDATED` | Designated validator explicitly confirms the answer |
| `ANSWERED` | `REJECTED` | Reviewer finds the answer insufficient |
| `VALIDATED` | `SUPERSEDED` | A newer validated answer replaces the current one |
| `REJECTED` | `UNANSWERED` | Question re-opened for new answer |
| `REJECTED` | `ANSWERED` | Revised answer provided in same or subsequent session |
| `VALIDATED` | `RESOLVED` | Managed by `/consolidate-knowledge` only |

No other transitions are permitted.

## Human Authority Principle

Evidence may support answers.

Evidence may suggest answers.

Evidence may never automatically close questions.

Human confirmation is mandatory for all transitions to ANSWERED, VALIDATED, or REJECTED.

A question status must not change without an explicit human action recorded in the current session.

A session record with no explicit human action does not constitute validation.

---

## Language Policy

### Language Normalization Rule

Human actors may provide validation responses in any language.

Before any response is written to a canonical artifact, the runtime produces an English-normalized version of the response.

### Human Confirmation Rule

The human actor must explicitly confirm that the English-normalized version correctly represents their intent before it is written to any canonical record.

This confirmation is a required application of the Human Authority Principle to the normalization step. Normalization without human confirmation must not be applied. A silently applied translation does not constitute validation.

### Canonical Record Rule

The `Answer`, `Evidence`, and `Decision` fields in canonical question records must contain English text only.

Non-English source text must not be written to canonical question record fields.

### Session Record Rule

Validation session records are canonical artifacts per ADR-001.

Session records must be written in English.

Original-language responses are not preserved inside session records.

The human's original-language response is not retained in any canonical artifact. Traceability to the original human intent is through the named actor recorded in `Validated By` and the source documents referenced in the `Evidence` field.

---

## Validation Session Model

A Validation Session is a discrete unit of human validation activity bounded by a single interaction.

Sessions are supporting traceability entities. They do not own questions. Questions persist independently of the sessions in which they receive input. A single question may receive input across multiple sessions.

### Session Record Fields

| Field | Description |
| ----- | ----------- |
| `session_id` | Unique session identifier — VS001, VS002, ... per workspace |
| `session_date` | ISO 8601 date of the session |
| `session_source` | Context or trigger for the session (e.g., stakeholder review, expert consultation, document review) |
| `actors` | Named human participants in the session |
| `questions_addressed` | List of question IDs addressed during the session |
| `evidence` | Supporting materials referenced during the session |
| `decisions` | Explicit decisions recorded during the session |

### Session ID Convention

Session IDs are sequential integers zero-padded to three digits, prefixed with `VS`:

```text
VS001, VS002, VS003, ...
```

IDs are assigned in order of session creation within a workspace. IDs do not reset across question report cycles.

---

## Answer Record Format

When a question receives an answer, the following fields are appended to the canonical question record in `questions_report.md`, below the existing Context block:

```markdown
**Answer:** <human-provided answer text>
**Answer Source:** <session_id>
**Answer Date:** <ISO 8601 date>
**Evidence:** <reference to supporting evidence, or 'None'>
**Decision:** <explicit decision text, or 'None'>
```

When a question reaches VALIDATED status, append:

```markdown
**Validated By:** <actor name or role>
**Validation Date:** <ISO 8601 date>
```

When a question is REJECTED, append:

```markdown
**Rejection Reason:** <reason the answer was found insufficient>
**Rejected By:** <actor name or role>
**Rejection Date:** <ISO 8601 date>
```

When a question is SUPERSEDED, the original answer block is preserved in full. A new answer block is appended with a supersession marker:

```markdown
**Superseded On:** <ISO 8601 date>
**Superseded By Session:** <session_id>

[new answer block follows, using the standard Answer Record Format above]
```

## Validation Session Record Format

Each session record must follow this structure:

```markdown
# Validation Session <session_id>

**Session Date:** <ISO 8601 date>
**Session Source:** <context or trigger>
**Actors:** <participant names or roles>

---

## Questions Addressed

| Question ID | Status Before | Status After | Answer Summary |
| ----------- | ------------- | ------------ | -------------- |
| Q001        | UNANSWERED    | ANSWERED     | <one-line summary> |

---

## Evidence

<list of supporting materials, with source references, or 'None'>

---

## Decisions

<list of explicit decisions recorded during the session, or 'None'>
```

## Severity Handling

| Severity | Validation Requirement |
| -------- | ---------------------- |
| BLOCKING | Must reach VALIDATED status before `/consolidate-knowledge` may proceed on the affected conflict. Human validation of BLOCKING questions is not deferrable. |
| ADVISORY | May proceed with a documented default resolution if the question is not answered. The default resolution must be recorded as a decision in the session record. |

## Preconditions

Before execution:

1. The repository structure must be valid.
2. The canonical question records must exist and be readable:

```text
workspaces/<workspace_id>/knowledge_base/questions/questions_report.md
```

3. At least one question with status `UNANSWERED`, `PARTIALLY_ANSWERED`, or `REJECTED` must exist in the question registry.
4. The validations directory must exist:

```text
workspaces/<workspace_id>/input/validations/
```

---

## Execution Rules

The command shall:

1. Read `workspaces/<workspace_id>/knowledge_base/questions/questions_report.md`.
2. Identify questions eligible for processing: status `UNANSWERED`, `PARTIALLY_ANSWERED`, or `REJECTED`.
3. Present each eligible question to the human actor for review and response.
4. For each question addressed: collect answer text, evidence references, and decisions from the human actor.
5. Determine the new status for each addressed question based on the human actor's explicit input.
6. Create a new validation session record with a new `session_id`.
7. Populate the session record with session metadata, questions addressed, evidence, and decisions.
8. Update the canonical question records in `questions_report.md` — append answer fields and update status.
9. Write the session record to `workspaces/<workspace_id>/input/validations/<session_id>.md`.

A session may address any subset of eligible questions. A session is not required to address all eligible questions in a single interaction.

If no eligible questions exist, report this explicitly and stop without creating a session record.

---

## Validation Rules

Each updated question record must:

* retain all original fields (question_id, conflict_id, type, severity, question text, context) unchanged;
* have a status drawn exclusively from the approved lifecycle states;
* have an `Answer Source` field referencing a valid session_id from the current session;
* have an `Answer Date` field;
* reach `VALIDATED` status only when explicitly confirmed by a named actor;
* never have its status changed without a corresponding session record.

Each validation session record must:

* have a unique `session_id` not previously used in the workspace;
* list all `question_id` values addressed in that session;
* list all actors who participated;
* be internally consistent with the corresponding question record updates.

---

## Failure Cases

The command must stop when:

* `workspaces/<workspace_id>/knowledge_base/questions/questions_report.md` does not exist;
* the question registry cannot be read;
* a session record cannot be written to `workspaces/<workspace_id>/input/validations/`;
* a requested status transition is not in the approved lifecycle transition table;
* repository structure is invalid;
* a question update cannot be traced to a session record.

Failures must be reported explicitly. Partial session writes must be rolled back or flagged as incomplete.

---

## Traceability Rules

Every answer record appended to a question must reference:

* the originating `question_id`;
* the originating `conflict_id` (available via the question record);
* the `session_id` in which the answer was recorded;
* the actor who provided the answer.

Questions that reach VALIDATED status must additionally reference:

* the actor who performed validation;
* the date of validation.

Every validation session record must reference:

* all `question_id` values addressed in that session;
* all evidence cited in support of any answer.

Traceability must remain intact for downstream stages: `/consolidate-knowledge` reads validated answer records to match answers back to originating conflict records.

---

## Completion Criteria

The command is complete when:

* at least one question has been addressed in the current session;
* a validation session record has been written to `workspaces/<workspace_id>/input/validations/<session_id>.md`;
* all questions addressed in the session have updated status and answer fields in `workspaces/<workspace_id>/knowledge_base/questions/questions_report.md`;
* every answer record is traceable to a session record;
* no question status was changed without an explicit human action recorded in the session.
