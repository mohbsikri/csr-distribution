# /validate-specification

## Purpose

Cross-check a specification artifact against its source knowledge artifact to assess content coverage. Produces a structured coverage report identifying business rules, technical rules, terms, and workflows present in the knowledge base that are absent or potentially missing from the specification.

This command is non-interactive, non-blocking, and read-only. It does not modify any specification artifact, lifecycle registry, or knowledge artifact. It is intended to be run by the human actor before `/specification-lifecycle BASELINE` as a voluntary quality signal.

---

## Inputs

```text
/validate-specification [<base>]
```

* `<base>` — optional; the specification base name. If omitted: uses the single eligible specification found in the active workspace. If multiple candidates exist and `<base>` is omitted: report `STATUS: VALIDATE BLOCKED — multiple candidates; specify <base>`.

---

## Target Specification

The command targets the specification at one of the following paths (in priority order):

1. `WORKSPACE_ROOT/specifications/draft/<base>_specification.md` — DRAFT (pre-BASELINE quality check)
2. `WORKSPACE_ROOT/specifications/stable/<base>_specification.md` — BASELINED (post-BASELINE audit)

If neither exists: `STATUS: VALIDATE BLOCKED — no specification found for <base>`.

---

## Source Knowledge Artifact

The knowledge artifact to compare against is resolved via the generation log:

```text
WORKSPACE_ROOT/specifications/draft/specifications_report.md
```

Read the `Source Artifact` field for the `<base>` row. If the generation log is absent or the row is not found: `STATUS: VALIDATE BLOCKED — cannot resolve source knowledge artifact`.

If the resolved knowledge artifact path does not exist: `STATUS: VALIDATE BLOCKED — knowledge artifact not found: <path>`.

---

## Outputs

Coverage report written to:

```text
WORKSPACE_ROOT/output/validation/<base>_spec_validation_<date>.md
```

The `output/validation/` directory is created if absent.

---

## Coverage Dimensions

The command checks four dimensions:

| Dimension | What is extracted from knowledge | What is checked in spec |
|-----------|----------------------------------|------------------------|
| Business Rules | All `**BR-NNN:**` entries | Pattern `BR-NNN` present in spec body |
| Technical Rules | All `**TR-NNN:**` entries | Pattern `TR-NNN` present in spec body |
| Terms | All term names under `# Terminology` or `# Terms` section | Term name present anywhere in spec body |
| Workflows | All named workflow headings under `# Workflows` section | Workflow name (or close variant) present in spec body |

---

## Coverage Report Format

```markdown
# Specification Coverage Report

**Base:** <base>
**Specification:** <spec_path> (<spec_status>)
**Knowledge Artifact:** <knowledge_path>
**Generated:** <date>
**Generated by:** /validate-specification

---

## Summary

| Dimension | In Knowledge | In Spec | Missing | Coverage |
|-----------|-------------|---------|---------|----------|
| Business Rules | N | N | N | N% |
| Technical Rules | N | N | N | N% |
| Terms | N | N | N | N% |
| Workflows | N | N | N | N% |

**Overall coverage:** N%

---

## Missing Items

### Business Rules

*(items present in knowledge artifact but not found in specification)*

- BR-NNN: <rule statement excerpt>

### Technical Rules

- TR-NNN: <rule statement excerpt>

### Terms

- <term>: <definition excerpt>

### Workflows

- <workflow name>

---

## Notes

<any warnings about parsing, ambiguous matches, or absent sections>
```

If all dimensions are 100% covered: the Missing Items section is omitted and the report states `All items covered`.

---

## Coverage Interpretation

Coverage percentages are informational only. No threshold triggers a failure. The human actor decides whether the coverage is acceptable before proceeding to BASELINE.

A missing item may be intentional (out of scope for this spec version) — the report surfaces it for human review, it does not block any operation.

---

## Workspace Resolution

Standard R4a–R4e workspace resolution applies.

---

## Execution Rules

1. Resolve workspace (W1–W5, R4a–R4e).
2. Locate target specification (DRAFT preferred over BASELINED).
3. Resolve source knowledge artifact via generation log.
4. Parse knowledge artifact — extract BR/TR IDs, term names, workflow names.
5. Parse specification body — build presence sets for each dimension.
6. Compute coverage per dimension.
7. Assemble coverage report.
8. Create `output/validation/` if absent.
9. Write coverage report.
10. Run validation rules SV1–SV6.
11. Report completion.

---

## Failure Cases

Stop and report `STATUS: VALIDATE BLOCKED` when:

* Workspace resolution fails.
* No specification found for `<base>`.
* Generation log absent or row not found.
* Knowledge artifact not found at resolved path.
* `output/validation/` cannot be created.
* Coverage report write fails.

---

## Completion Reporting

```text
STATUS: VALIDATE COMPLETE
STATUS: VALIDATE BLOCKED
```

---

## Validation Rules

| Rule | Check | Class |
|------|-------|-------|
| SV1 | Coverage report exists at declared output path and is readable | BLOCKING |
| SV2 | All four dimensions are present in the report Summary table | BLOCKING |
| SV3 | No write operations targeted any path outside `WORKSPACE_ROOT/output/validation/` | BLOCKING |
| SV4 | Specification artifact was not modified during execution | BLOCKING |
| SV5 | Knowledge artifact was not modified during execution | BLOCKING |
| SV6 | Report `<base>` and `<spec_path>` fields match the actual files read | WARNING |
