# /generate-views — Execution Specification

## Runtime

### Phase 0 — Load L3 Prompt

Before generating any view, read and assimilate:

```text
templates/commands/generate_views_prompt.md
```

This file defines:
- The complete section structure for each document type (SF, DAT, STD, QA)
- Mermaid diagram templates per section
- [GAP] block format and criticality rules
- Document naming map (internal view IDs → professional file names)
- Bilingual generation rules
- Cover page HTML format
- Revision History generation rules (DQM-2)
- QA sections QA-03c through QA-03f and QA-07b/QA-07c (DOC-RT-01)
- SF-04b Hypothèses et dépendances section (DOC-RT-06)
- DAT-03b Stratégie architecturale, DAT-08b Concepts transversaux, DAT-09b Exigences qualité (DOC-RT-04)

All section structures, diagram instructions, and [GAP] rules in that file take precedence over general conventions.

### Phase 1 — Workspace Resolution

Standard W1–W5 workspace resolution. All subsequent paths are prefixed with `WORKSPACE_ROOT`.

Read workspace configuration from `WORKSPACE_ROOT/runtime/workspace_config.md`:
- `primary_language` — determines which language file is generated first
- `theme` — recorded in the generation report (used by /export-views)
- `logo_path` — if present, included in cover page img tag
- `workspace_description` — used in cover page subtitle

> **Corrected 2026-11-01 (A3).** This block previously named `runtime/workspaces.md`, the repository-wide workspace registry. That file carries none of these four fields — its columns are `workspace_id`, `created`, `status`, `description`, `last_active`, `runtime_version`, `spec_template_version`. All four live in the per-workspace `runtime/workspace_config.md`, written by `/workspace-lifecycle`. A reader following the old instruction found nothing and silently generated a cover page with no logo, no subtitle and a default language — the failure mode of a path that is wrong rather than missing.

If `workspace_config.md` is absent: proceed with `primary_language` = workspace default, `theme` = `default`, no logo and no subtitle. Report the absence; do not stop.

### Phase 2 — Load Canonical Specification

1. Locate `WORKSPACE_ROOT/specifications/stable/<base>_specification.md`.
   - If not found: BLOCKED — canonical specification not found. Stop.
2. Read the specification. **Detect spec format** (`spec_format`):
   - First non-empty line is exactly `---` → `spec_format = STD` (YAML frontmatter present; generated by /generate-specification in STD mode and BASELINED by /specification-lifecycle)
   - Any other first non-empty line → `spec_format = LEGACY`
3. **Verify BASELINED status** (routing by `spec_format`):
   - STD: parse `status:` field from the YAML frontmatter block (the content between the opening `---` and the closing `---`). If `status ≠ BASELINED`: BLOCKED — canonical specification is not BASELINED.
   - LEGACY: parse `**Status:**` Markdown bold header field. If `status ≠ BASELINED`: BLOCKED.
4. **Parse spec_id and baseline_date** (routing by `spec_format`):
   - STD: parse `spec_id:` and `baseline_date:` from the YAML frontmatter block.
   - LEGACY: parse `**Spec ID:**` and `**Baseline Date:**` from the Markdown bold header block.
   Record both for use in view headers and cover pages.
5. **Define body boundary** (routing by `spec_format`):
   - STD: body = all content strictly after the YAML closing `---` (the second line that is exactly `---` at the start of the file). The YAML frontmatter block itself is excluded from body parsing and must never appear as rendered content in any generated view.
   - LEGACY: body = all content after the first `---` separator.
6. Parse all specification sections from body. Load content for view scoping:
   - STD: use the STD section content map built in Phase 2c.
   - LEGACY: parse the 7-section structure (`## 1. Terms and Definitions`, `## 2. Context and Background`, `## 3. Design Decisions`, `## 4. Assumptions`, `## 5. Constraints`, `## 6. Business Rules`, `## 7. Technical Rules`).
7. Count items for [GAP] threshold decisions:
   - STD: count BR-NNN rows (Section 5.1), TR-NNN rows (Section 5.2), FR-NNN rows (Section 6), AC-NNN rows (Section 7), NFR-NNN rows (Section 11), OP-NNN rows (Section 13).
   - LEGACY: count BR-NNN, TR-NNN, C-NNN.

### Phase 2b — Parse KPM and Inference Registry

From the canonical specification loaded in Phase 2, build the following structures for audience-aware view filtering (ADR-004 WP-4 — KPM Filtering Policy):

**Step 1 — KPM Status**

- STD: parse `**KPM Status:**` from the generation metadata block, which occupies the first lines of the spec body immediately after the YAML closing `---` (the block contains 7 Markdown bold fields: `**Source Artifact:**`, `**Source Type:**`, `**Generated:**`, `**Generation Command:**`, `**Conflicts Incorporated:**`, `**Questions Incorporated:**`, `**KPM Status:**`).
- LEGACY: parse `**KPM Status:**` from the Markdown bold header block (before the first `---` separator in body).

In both cases, record as `kpm_status`:
- `PROVENANCE_INDEXED` — extraction-level provenance tracked
- `NO_PROVENANCE_INDEX` — T-MODE, no provenance index
- Absent — treat as `NO_PROVENANCE_INDEX`

**Step 2 — Parse Inference Registry subsections**

- STD: locate `## Annexe A — Inference Registry` heading in the spec body.
- LEGACY: locate `## Inference Registry` heading.

For each subsection, parse table rows. If a subsection is absent or contains only `*(aucun élément)*`: corresponding list is `[]`.

```text
ir_structural[]        ← rows from "### INFERRED_DESIGN — Impact Structurel"
                          each: { element, rationale, statut }
ir_implementation[]    ← rows from "### INFERRED_DESIGN — Détail d'Implémentation"
                          each: { element, rationale, statut }
ir_tech_standard[]     ← rows from "### TECH_STANDARD"
ir_undefined[]         ← rows from "### UNDEFINED_IN_SOURCE"
```

**Step 3 — Derive filtering indices**

```text
ir_pending_structural[] = filter ir_structural[] where statut = "PENDING_VALIDATION"
ir_all_entries[]        = ir_structural[] ∪ ir_implementation[] ∪ ir_tech_standard[] ∪ ir_undefined[]
ir_has_blocking         = (ir_pending_structural[].length > 0)
```

These structures are passed to all view generation phases (4–7) for filtering per the KPM Filtering Policy in `templates/commands/generate_views_prompt.md`.

If `## Inference Registry` section is absent from the spec: all lists are `[]`; `ir_has_blocking = false`. Non-blocking — proceed normally (T-MODE path).

**Content bucket rules:**
- `stm_br`, `stm_tr`, `stm_fr`, `stm_ac`, `stm_nfr`, `stm_open_points` are table row lists — each bucket contains parsed rows from the respective section's Markdown table.
- **Column names are bilingual, and the English spellings were never specified until now.** `/generate-specification` emits an `_en` and an `_fr` variant of the same canonical specification, and the English one translates its headers — `FR Covered`, `Status` — a behaviour no contract layer described, so each run re-invented it. Every reader must accept both spellings, and the one legacy alias:

  | Canonical (fr) | English | Legacy alias |
  |---|---|---|
  | `FR Couvert` | `FR Covered` | — |
  | `Source` (Section 7) | `Source` | `Statut` · `Status` — renamed 2026-11-01 |
  | `Statut` (Sections 5, 6, 11) | `Status` | — |
  | `Preuve` | `Proof` | — |
  | `Démontré en` | `Demonstrated in` | — |
  | `Mesuré` | `Measured` | — |

- **Parse every table column by NAME, never by position.** Sections 7 and 11 gained columns with ADR-007; a positional parser reads the wrong field and fails silently. A specification baselined before ADR-007 has no `Preuve` column at all — treat its absence as `NON_DÉMONTRÉ`, never as an error.
- `stm_proof` is **rendered, never recomputed**. The canonical holds machine-readable values; QA-04 copies them verbatim (they are the test result), while SF-10 and DAT-09b translate them into a business sentence per the mapping in the L3 prompt. A proof scope must survive the translation: `DÉMONTRÉ` + `UAT` renders as *Démontré en UAT*, never as *Démontré* — dropping the scope lets a reader conclude production.
- `stm_actors` contains the full actor table (columns: Rôle, Description, Droits principaux, Volume estimé).
- All other buckets contain the raw Markdown content of the section.

### Phase 2d — Parse Lifecycle Registry for Revision History (DQM-2)

Parse the workspace lifecycle registry to build the revision history for all four human-facing views (ADR-006 DQM-2).

**Source (primary):** `WORKSPACE_ROOT/specifications/lifecycle/specifications_lifecycle.md` — the per-workspace specification lifecycle registry.

- Locate all events with `Event Type: BASELINE` for the current `spec_id` and `base`, in chronological order of their Event ID.
- First BASELINE event = INITIAL_BASELINE. All subsequent BASELINE events for the same spec_id = EVOLVE_BASELINE (each linked to a completed EVOLVE cycle via `evolve_id:`).

**Source (fallback — when no lifecycle registry file exists):** Use the `baseline_date:` field already parsed from the YAML frontmatter in Phase 2 as the single INITIAL_BASELINE event. This covers workspaces created before the lifecycle registry was introduced (e.g., std-real-01, std-synth-01).

**Parse rule:** Collect all BASELINE events for the current spec (primary path) or the single `baseline_date:` value (fallback path). Record as:

```text
lifecycle_baseline_events[] ← array of { type, date, description }
  type        : "INITIAL_BASELINE" | "EVOLVE_BASELINE"
  date        : ISO date string (YYYY-MM-DD)
  description : evolution summary from EVOLVE registry entry, or "—" if not available
```

**Derive revision_history_rows[]:**

```text
revision_history_rows[] ← from lifecycle_baseline_events[]
  INITIAL_BASELINE → Version = "v1.0", Nature = "Baseline initiale", Description = "Première version officielle"
  1st EVOLVE_BASELINE → Version = "v2.0", Nature = <derived, see below>, Description = <from registry or "—">
  2nd EVOLVE_BASELINE → Version = "v3.0", ...
```

**Nature of an evolution (E7).** A version number says the document changed; it does not say whether the **system being specified** changed. A reader who must re-plan on a functional change, and need not on a documentary one, cannot tell them apart from `v2.0` alone. Derive from the element families the EVOLVE change set actually touched:

```text
functional_families = { BR, TR, D, FR, NFR }                    # the specified system
ac_substance        = { Given, When, Then } columns of AC       # what the system must satisfy
nfr_substance       = { Seuil } column of NFR

if change_set touches any functional_families element,
   or any ac_substance / nfr_substance cell:
     Nature = "Évolution fonctionnelle"
else:
     Nature = "Évolution documentaire"
```

Read the change set from the EVOLVE registry entry identified by `evolve_id:` on the BASELINE event. **If the change set cannot be read, write `"Évolution"`** — the unqualified value this field carried before E7. Do not guess: an evolution wrongly labelled documentary tells a reader they need not look, which is the one error this field exists to prevent.

`Corrective` is deliberately **not** in the derived vocabulary. Whether a change fixed an error is a judgement about intent, not a fact readable from a change set; inventing it would be inventing content. A human may write it into the registry description; CSR may not derive it.

Consistent with ADR-007 Engagement #6: filling a `Preuve` field is not a specification change, produces no new BASELINE event, and therefore produces no revision history row at all — neither functional nor documentary.

**If no INITIAL_BASELINE event found:** `revision_history_rows[] = []` — the Revision History section (SF-01b / DAT-01b / STD-01b / QA-01b) is **omitted from all views**. This is not a `[GAP]` condition. It occurs when generating views from a spec that has not yet been formally baselined (CANDIDATE or DRAFT state). Note: Phase 2 already blocks generation if spec status ≠ BASELINED; in practice `revision_history_rows[]` will always be non-empty when this phase completes.

**Note on lifecycle event names:** In the CSR BASELINE/REOPEN/EVOLVE lifecycle model (ADR-001/ADR-002), `INITIAL_BASELINE` corresponds to the first successful `/specification-lifecycle BASELINE` command on a spec, and `EVOLVE_BASELINE` corresponds to the terminal step of a completed EVOLVE cycle (state `EVOLVE_BASELINE` in the lifecycle registry).

### Phase 7 — Generate View: Agent IA

Apply Agent IA content scope and format per ADR-003. Write Structured Markdown with YAML front-matter and typed bracket identifiers.

**YAML front-matter (mandatory):**
```yaml
---
spec_id: <SP-ID>
base: <base-name>
audience: agent
canonical_ref: specifications/stable/<base>_specification.md
canonical_status: BASELINED
version: <spec_id>
generated: <ISO date>

```

**Content blocks (mandatory where data exists in canonical spec):**

* `ACTOR[]` — one block per actor role; include permissions
* `ENTITY[]` — one block per Dataverse table; include pk, field list with typed references
* `STATE_MACHINE[]` — one block per lifecycle state machine; include all valid transitions with ACTOR[] and RULE[] references
* `WORKFLOW[]` — one block per workflow; include actors, trigger, terminal state, step sequence with ACTOR[], STATE[], CONDITION[], RULE[] references
* `RULE[]` — one block per business rule (BR-nnn), technical rule (TR-nnn); for LEGACY specs also one block per constraint (C-nnn); include type, statement, applies_to, formula/regex when applicable, cross_ref
* `TERM[]` — one block per key term; include single-sentence definition, schema_ref when a Dataverse entity, cross_ref to related RULE[] or ENTITY[]

**STD spec additions (when `spec_format = STD`):** After the standard RULE[] blocks, also emit:

* `REQUIREMENT[]` — one block per FR-NNN from `stm_fr`; include `id`, `description`, `br_source`, `priority`, `domaine`, `source` (DK/SF/ID), `statut`
* `ACCEPTANCE[]` — one block per AC-NNN from `stm_ac`; include `id`, `fr_covered`, `given`, `when`, `then`, `statut`
* `NFR[]` — one block per NFR-NNN from `stm_nfr`; include `id`, `category`, `description`, `seuil`, `source`, `statut`
* `OPEN_POINT[]` — one block per OP-NNN from `stm_open_points`; include `id`, `description`, `priorite`, `statut`

In STD mode, C-NNN is deprecated at spec level; emit no RULE[] blocks for C-NNN. NFR-NNN replaces C-NNN constraints in the typed block registry.

**Format invariants:**
* Every reference uses typed bracket notation: `ENTITY[]`, `RULE[]`, `ACTOR[]`, `STATE[]`, `SCREEN[]`, `WORKFLOW[]`, `TERM[]`, `CONSTRAINT[]`
* No pronouns, no "as mentioned above", no implicit references
* Every rule carries a stable, unique ID (`BR-001`, `TR-001`, `C-001`)
* No narrative prose — every line is a fact, rule, or structural element
* State machine transitions: every valid transition listed; absent = blocked

**KPM coverage — no filtering (complete verbatim):**

After all ENTITY[], RULE[], WORKFLOW[] blocks, emit an `INFERENCE_REGISTRY[]` block using `ir_all_entries[]` from Phase 2b. No filtering applies to the view_agent artifact.

Format (Markdown structured block, not YAML):

If all lists in `ir_all_entries[]` are empty (T-MODE): emit `INFERENCE_REGISTRY[kpm_status: NO_PROVENANCE_INDEX]: none` — this is the expected T-MODE non-regression output.

Write to `WORKSPACE_ROOT/specifications/views/<base>_view_agent.md`.
