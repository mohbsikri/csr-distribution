# /specification-lifecycle

## Purpose

Govern the post-generation lifecycle of draft specification artifacts.

This command implements Stage 8 — Specification Stabilization of the CSR pipeline as defined in `docs/operating_model.md`.

The lifecycle layer assigns formal, traceable states to specification artifacts, establishes the conditions under which a specification becomes a committed baseline, and defines the paths available when new information arrives for an already-baselined specification.

This command is **interactive**. All lifecycle transitions require explicit human authorization. The runtime surfaces the current specification state and the available transitions; the human actor makes the decision and provides the required metadata. The runtime records the decision; it does not make it.

The lifecycle layer is the necessary foundation for future change management. A specification can only be meaningfully changed relative to a defined baseline. The lifecycle layer establishes that reference point.

---

## Supported Operations

| Operation | Trigger Condition | Description |
|-----------|------------------|-------------|
| BASELINE | Specification is DRAFT | Promote to committed reference version |
| BASELINE V2 | EVOLVE_PENDING active in Lifecycle Registry for `<base>` | Promote Candidate V2 to Baseline V2; version Baseline V1 as SUPERSEDED; transition Change Set to COMPLETE |
| REOPEN | Specification is BASELINED | Return to DRAFT for correction; same identity retained |
| EVOLVE | Specification is BASELINED | Create new DRAFT version; preserve prior baseline |
| ARCHIVE | Specification is BASELINED | Retire; terminal state; full lineage moved to `specifications/archive/` |

**BASELINE V2 mode** is activated automatically when `/specification-lifecycle BASELINE` detects an active EVOLVE_PENDING event in the Lifecycle Registry for `<base>` (written by `/evolve-specification` Phase P6 — WP-EVOLVE-1F). In BASELINE V2 mode, eligibility conditions E1–E7 are replaced by E6 V2 (impact-aware inference validation) and E7 V2 (candidate coherence review). See `docs/commands/specification-lifecycle_execution.md` — BASELINE V2 — EVOLVE_PENDING Mode section.

## Lifecycle States

A specification artifact holds one of four formal lifecycle states at any time.

---

### DRAFT

**Meaning:** The specification has been generated by `/generate-specification` but has not been formally reviewed and frozen. Its content may change as upstream consolidated knowledge is updated and the specification is re-generated.

**Entry:** Created automatically by `/generate-specification`.

**Ownership:** Runtime on entry. Human actor is responsible for deciding when to promote.

**Allowed transitions:**

| Transition | Trigger |
|------------|---------|
| DRAFT → BASELINED | Explicit human BASELINE decision |

**Invariants:**

- All specifications begin as DRAFT.
- A DRAFT specification is not a reference for downstream work.
- A DRAFT specification may be re-generated from updated upstream artifacts any number of times.
- A DRAFT specification may coexist with a BASELINED specification of the same `<base>` only during the EVOLVE path, while the new version is under development.

---

### BASELINED

**Meaning:** The specification has been explicitly approved and frozen by a named human actor. It represents a committed reference version. Downstream work may be started against a BASELINED specification.

**Entry:** Explicit human BASELINE decision via this command.

**Ownership:** Human actor. Only a named human actor may authorize entry or exit from this state.

**Allowed transitions:**

| Transition | Trigger |
|------------|---------|
| BASELINED → DRAFT | Explicit human REOPEN decision |
| BASELINED → SUPERSEDED | Runtime, during EVOLVE execution |
| BASELINED → ARCHIVED | Explicit human ARCHIVE decision |

**Invariants:**

- Only one non-SUPERSEDED specification per `<base>` may hold BASELINED status at a time.
- A BASELINED specification must not be modified in-place without an explicit REOPEN or EVOLVE decision.
- A BASELINED specification resides in `WORKSPACE_ROOT/specifications/stable/<base>_specification.md`.

---

### SUPERSEDED

**Meaning:** A newer version of this specification has been created via the EVOLVE path. This version is preserved in full for traceability but is no longer the active reference for downstream work.

**Entry:** Runtime, when the EVOLVE path is executed against the current BASELINED version.

**Ownership:** Runtime on entry. No human action is required to enter this state.

**Allowed transitions:** None. SUPERSEDED artifacts are moved to `specifications/archive/` as part of the ARCHIVE operation applied to the BASELINED base — not through a direct transition on the SUPERSEDED artifact.

**Invariants:**

- A SUPERSEDED specification must not be modified.
- A SUPERSEDED specification must remain readable indefinitely. It must not be deleted.
- A SUPERSEDED specification retains its artifact content verbatim from the moment it was superseded.
- A SUPERSEDED specification carries a `**Superseded By:**` header field pointing to the artifact that superseded it.
- SUPERSEDED specifications reside in `WORKSPACE_ROOT/specifications/stable/<base>_specification_v<n>.md`.

---

### ARCHIVED

**Meaning:** The specification is no longer actively maintained. It is preserved for historical reference and audit only.

**Entry:** Explicit human ARCHIVE decision.

**Ownership:** Human actor.

**Allowed transitions:** None. ARCHIVED is a terminal state.

**Invariants:**

- An ARCHIVED specification must not be re-activated. If its content is needed again, a new specification must be created from a new pipeline run.
- An ARCHIVED specification must remain readable.

---

## Baseline Concept

A **baseline** is a human-authorized commitment that a specification represents an agreed-upon reference version.

A baseline is not a consequence of generation. `/generate-specification` produces DRAFT artifacts. Generation alone establishes content; it does not establish commitment.

**Why the baseline concept exists:**

The operating model's core rule states: *"No specification should become stable without explicit validation."* The baseline is that explicit validation act. Without it, there is no distinction between a specification that is being worked on and one that has been committed to. Change management requires a defined reference point to manage changes against; the baseline is that reference point.

**Baseline eligibility conditions:**

A specification is eligible for baselining when all of the following hold:

| ID | Condition | Check |
|----|-----------|-------|
| E1 | Status is DRAFT | **Legacy spec:** artifact `**Status:**` field must be DRAFT. **STD spec** (first line is `---`): YAML `status:` field must be `DRAFT`. |
| E2 | Artifact exists and is readable | File exists at the declared draft path |
| E3 | All BLOCKING conflicts are CONSOLIDATED | For each `conflict_id` in `**Conflicts Incorporated:**`: status must be CONSOLIDATED in `consolidation_report.md` |
| E4 | Named human authorization provided | Actor name, baseline date, and optional rationale received |
| E5 | No other BASELINED version exists for this `<base>` | Lifecycle registry has no active BASELINED entry for `<base>` |
| E6 | Inference Registry contains no INFERRED_DESIGN structural PENDING_VALIDATION element (extended: writes D7 to sqf_gate_report.md) | Read `### INFERRED_DESIGN — Impact Structurel` in the draft specification's Inference Registry. For every row where `Statut = PENDING_VALIDATION`: this element blocks BASELINE (ADR-004 Engagement #6). **SQF Extension:** after computing the E6 result, compute I7.1 (= E6 result) and I7.3 (HITL validation rate) and write the D7 section of `sqf_gate_report.md`; update `gate_status` to the global worst-of(D1, D3, D7). |
| E7 | SQF Q-GATE-1 gate_status is not BLOCK | Read `specifications/draft/sqf_gate_report.md`. If absent: WARN (legacy mode — see below). If `gate_status = BLOCK`: BASELINE REFUSED. If `gate_status = WARN`: BASELINE proceeds with sqf_warn recorded in lifecycle event. If `gate_status = PASS`: BASELINE proceeds. |

**The `Preuve` columns of Sections 7 and 11 are not a baseline condition, and must never become one (ADR-007 §5.1).** No eligibility condition reads them. A specification whose every acceptance criterion is `NON_DÉMONTRÉ` is fully eligible for BASELINE.

The distinction is deliberate and worth stating, because the two cases look alike and are opposites. E6 blocks on `PENDING_VALIDATION` because something is **missing from the specification** — a structural design decision nobody has validated. `NON_DÉMONTRÉ` says the opposite: the specification is complete, and **the world has not caught up**. A freshly baselined specification is supposed to be entirely undemonstrated — the system it describes does not exist yet. Gating on it would make BASELINE unreachable until after delivery, which inverts the purpose of a baseline.

`INFIRMÉ` is a different matter: a baselined specification carrying a criterion demonstrated false is a real contradiction between the document and the system. It is detected after the fact by `tools/csr-check` (W-family), not by a baseline gate — the contradiction normally appears long after BASELINE, when the test is run.

**E6 remains the only authoritative evaluation of D7 (R11, 2026-11-01).** `/generate-specification` now writes a non-binding *advisory* D7 reading into the draft gate report, so that a specification left in draft is not without any D7 signal. That reading is informational and is recomputed here from scratch: it may have been taken days earlier, before a validation session moved elements out of `PENDING_VALIDATION`. A `BLOCK` advisory routinely precedes a `PASS` gate, and nothing is wrong when it does. Never substitute the advisory value for the E6 result, and never skip E6 because an advisory reading exists.

Condition E3 is verified by `/generate-specification` at generation time. It must be re-verified at baseline time because upstream pipeline state may have changed since generation.

Condition E6 (Inference Governance Gate — ADR-004 Engagement #6) is verified at baseline time by reading the `### INFERRED_DESIGN — Impact Structurel` subsection of the draft specification's Inference Registry. If this subsection contains one or more rows where `Statut = PENDING_VALIDATION`, the specification is not eligible for BASELINE. These are structural design decisions introduced during specification generation (Step 6.5b of `/generate-specification`) that have not yet been validated by a project stakeholder. Elements in `### INFERRED_DESIGN — Détail d'Implémentation` with `governance_status = REGISTERED` (implementation-level decisions) do not block BASELINE. If E6 fails, BASELINE is refused and the blocking elements are listed with resolution paths (see `docs/commands/specification-lifecycle_execution.md` Phase 3 Step E6 for the exact message format). The E6 extension (SQF Phase 1) additionally writes I7.1 and I7.3 scores to `sqf_gate_report.md` without changing the blocking logic.

Condition E7 (SQF Quality Gate — SQF Phase 1) is verified after E6. It checks the global `gate_status` in `sqf_gate_report.md`. A BLOCK gate_status at E7 means D1 or D3 produced a blocking score during `/generate-specification` Phase 7; BASELINE is refused regardless of E6 outcome. On WARN, BASELINE proceeds and `sqf_warn=true` with `warn_dimensions` is recorded in the lifecycle event.

**Legacy workspace behavior (E7):** If `sqf_gate_report.md` is absent (workspace predates SQF Phase 1), E7 produces a WARNING and BASELINE proceeds in legacy mode. The lifecycle event records `sqf_legacy=true`. This mirrors the T-MODE pattern established by ADR-004. Recommendation: run `/generate-specification` on the evolved version before the next EVOLVE cycle.

**What baselining does not do:**

- It does not verify that downstream work has not started.
- It does not lock the upstream knowledge base from modification.
- It does not prevent new source material from being ingested.
- It does not create copies of upstream consolidated or extracted artifacts.

Human governance is responsible for baseline timing decisions. The runtime enforces eligibility conditions; it does not enforce readiness.

## REOPEN Decision

**Definition:** The REOPEN path revokes the current baseline, returns the specification to DRAFT, and preserves the same specification identity for correction through the standard pipeline.

**When allowed:** The specification has status BASELINED. A named human actor explicitly chooses REOPEN.

**Required human input:** actor name, reopen date, reopen reason.

**Expected outcome:**

1. The specification's status transitions from BASELINED to DRAFT.
2. Baseline metadata is cleared: for legacy specs, `**Baseline Date:**`, `**Baselined By:**`, and `**Baseline Rationale:**` are removed from the artifact header; for STD specs, YAML `status:` returns to `DRAFT` and `baseline_date:` is set to `null`.
3. The prior baseline event is retained permanently in the lifecycle registry — not deleted.
4. A REOPEN event is recorded in the lifecycle registry with actor name, date, and reason.
5. The specification identity (spec ID, artifact path in the draft directory) is preserved.
6. The specification may be re-generated from updated upstream consolidated knowledge using `/generate-specification`.

**What REOPEN does not do:**

- It does not restore any prior version of the specification content.
- It does not notify downstream consumers that the baseline has been revoked.
- It does not revert any upstream artifacts.

**Guidance (not enforced by the runtime):** REOPEN is appropriate when the change is a correction to a content error, no downstream work has been started against the baseline, and the time since baselining is short. The human actor is responsible for ensuring REOPEN is the appropriate path.

---

## EVOLVE Decision

**Definition:** The EVOLVE path preserves the existing BASELINED specification as a versioned historical record (SUPERSEDED) and creates a new specification version in DRAFT state for independent development.

**When allowed:** The specification has status BASELINED. A named human actor explicitly chooses EVOLVE.

**Required human input:** actor name, evolution date, evolution reason.

**Expected outcome:**

1. The existing BASELINED specification transitions to SUPERSEDED.
2. The SUPERSEDED artifact is preserved at a versioned path within `WORKSPACE_ROOT/specifications/stable/`, following the convention `<base>_specification_v<n>.md` where `<n>` is assigned by the lifecycle registry.
3. The active baseline slot (`specifications/stable/<base>_specification.md`) is vacated.
4. A new DRAFT specification stub is created at `specifications/draft/<base>_specification.md`. It carries:
   - `**Status:** DRAFT`
   - `**Supersedes:** specifications/stable/<base>_specification_v<n>.md`
   - A new Spec ID assigned by the lifecycle registry
5. An EVOLVE event is recorded in the lifecycle registry.
6. New source material may now be ingested and processed through the standard pipeline for this `<base>`. A new generation run of `/generate-specification` produces the evolved specification content.

**What EVOLVE does not do:**

- It does not automatically re-run the upstream pipeline.
- It does not generate the new specification content.
- It does not copy or version upstream knowledge base artifacts.

## Versioning Convention

The active baseline is always at the unsuffixed path:

```text
specifications/stable/<base>_specification.md
```

When superseded by an EVOLVE operation, the prior baseline is renamed to a versioned path:

```text
specifications/stable/<base>_specification_v<n>.md
```

Where `<n>` equals the baseline sequence number assigned by the lifecycle registry at the time of supersession. The lifecycle registry maintains a `version_sequence` counter per `<base>`, incremented by each BASELINE operation.

Version number assignment:
- BASELINE increments `version_sequence` for `<base>`
- EVOLVE uses the current `version_sequence` as the suffix for the SUPERSEDED artifact

## Traceability

All lifecycle decisions must remain permanently traceable.

**Required fields per lifecycle state:**

| State | Header field | Value |
|-------|-------------|-------|
| BASELINED | `**Baseline Date:**` | ISO 8601 date |
| BASELINED | `**Baselined By:**` | Named actor |
| BASELINED | `**Baseline Rationale:**` | Text or "—" |
| SUPERSEDED | `**Superseded By:**` | Path to superseding artifact |
| SUPERSEDED | `**Superseded Date:**` | ISO 8601 date |
| DRAFT (evolved) | `**Supersedes:**` | Path to SUPERSEDED artifact |
| ARCHIVED | `**Archived Date:**` | ISO 8601 date |
| ARCHIVED | `**Archived By:**` | Named actor |
| ARCHIVED | `**Archive Reason:**` | Text |

**STD spec traceability:** For STD specs (`spec_mode = STD`), lifecycle state is recorded in the YAML `status:` field. The `baseline_date:` YAML field is set on BASELINE and set to `null` on REOPEN. All other traceability metadata (actor names, rationale, lineage paths) is recorded exclusively in the lifecycle registry Event Log. The Markdown bold fields listed above are not written to STD artifact bodies. The lifecycle registry is the authoritative source for this metadata.

**Extended traceability chain:**

```text
stable specification (BASELINED)
  → lifecycle registry (baseline event: actor, date, rationale)
    → generation log (spec_id → source artifact, conflicts, questions)
      → consolidation report (conflict_id → consolidated artifact)
        → questions report (question_id → validation session)
          → validation session record (answer, evidence, validator)
            → source document (origin_path)
```

For SUPERSEDED specifications, the chain extends backward through lineage:

```text
stable specification v2 (BASELINED)
  → Supersedes header → v1 (SUPERSEDED)
    → lifecycle registry (evolve event: actor, date, reason)
      → standard traceability chain for v1
```

**Lifecycle registry is authoritative:** In the event of a discrepancy between the registry and an artifact's `**Status:**` header field, the registry takes precedence. The discrepancy must be reported and the artifact corrected.

## Language Policy

Lifecycle event records are canonical CSR artifacts. All lifecycle records must be written in English, consistent with ADR-001 (CSR Language Policy).

Lifecycle decision text (rationale, reason fields) is human-authored. If provided in a language other than English, the normalization principle from Stage 5 (Human Validation) applies: an English-normalized version is produced and confirmed by the human actor before writing to the lifecycle registry.

## STD Spec Detection

A specification is a **STD spec** if its first line is exactly `---` (YAML frontmatter opener, as produced by `templates/spec_canonical_v1.md`). All other specifications are **legacy specs**.

Upon reading any target specification artifact, immediately determine `spec_mode`:

| First line of artifact | `spec_mode` | Status field location | Body boundary |
|------------------------|-------------|----------------------|---------------|
| `---` (exactly) | STD | YAML `status:` field (inside frontmatter block) | Content below the YAML closing `---` (second `---`) |
| anything else | LEGACY | `**Status:**` Markdown bold header | Content below the first `---` separator |

`spec_mode` governs all status field reads, header writes, and body boundary detection throughout the execution.

**Lifecycle writes to STD artifact YAML fields:**
- BASELINE: `status: BASELINED`, `baseline_date: <date>`
- REOPEN: `status: DRAFT`, `baseline_date: null`
- EVOLVE (versioned SUPERSEDED artifact): `status: SUPERSEDED`
- ARCHIVE: `status: ARCHIVED`

For STD specs, all traceability metadata (actor names, rationale, lineage paths, dates beyond `baseline_date`) is recorded exclusively in the lifecycle registry Event Log. The Markdown bold traceability fields (`**Baselined By:**`, `**Baseline Rationale:**`, `**Superseded By:**`, `**Superseded Date:**`, `**Archived By:**`, `**Archive Reason:**`) are **not** written to STD artifact bodies.

|----|-------------|------|-------------------|

| P3 | `WORKSPACE_ROOT/specifications/stable/<base>_specification.md` exists and is readable | REOPEN, EVOLVE | Stop. Report missing stable specification. |

## Failure Cases

Stop execution when:

- Workspace runtime fails to resolve.
- Target specification does not exist or is unreadable.
- Target specification status is incompatible with the requested operation.
- Any BASELINE eligibility condition (E1–E6) fails — state the failing condition explicitly.
- A write failure occurs on any output artifact.
- A registry write failure occurs after file operations have been performed — append a LIFECYCLE FAILURE NOTE to the affected artifact; report BLOCKED.
- A workspace isolation violation occurs.

Do not silently continue after any blocking failure. Every failure must be named and reported.

---

## Constraints

- The lifecycle registry must not be modified by any command other than `/specification-lifecycle`.
- No specification body content may be altered by lifecycle operations. Only header fields are modified. **Legacy specs:** content below the first `---` separator is unchanged. **STD specs** (first line is `---`): only YAML frontmatter fields (`status:` and `baseline_date:`) are modified; content below the YAML closing `---` (second `---`) is unchanged.
- All write operations must target paths within `WORKSPACE_ROOT/specifications/` (draft, stable, lifecycle, or archive sub-directories).
- Upstream artifacts (`knowledge_base/`, `input/`) must not be modified by lifecycle operations.
- A SUPERSEDED specification must not be deleted.
- An ARCHIVED specification must not be deleted.
- The lifecycle registry is append-only for event records. Prior events must not be overwritten or removed.

---

## Traceability Matrix Co-movement

**Traceability Matrix Co-movement:**
When performing any MOVE operation (BASELINE, REOPEN, EVOLVE, ARCHIVE), the traceability matrix file is moved alongside the specification if it exists at the expected source path. If the traceability file is absent, the operation continues without error (non-blocking).

Expected source and destination paths follow the same directory transitions as the specification file, using the `<base>_traceability[_v<n>].md` naming pattern.

Expected paths by lifecycle state:
- DRAFT state: `specifications/draft/<base>_traceability.md`
- BASELINED state: `specifications/stable/<base>_traceability.md`
- SUPERSEDED (EVOLVE): `specifications/stable/<base>_traceability_v<n>.md` (versioned with the superseded spec)
- ARCHIVED: `specifications/archive/<base>_traceability.md`

## Post-Execution Validation Rules

| Rule | Check | Class |
|------|-------|-------|
| BL1 | Every BASELINED specification has a corresponding entry in the lifecycle registry with `baseline_date` and `baselined_by` populated. | BLOCKING |
| BL2 | Every BASELINED specification file exists at its declared stable path and is readable. | BLOCKING |
| BL3 | No two non-SUPERSEDED specifications for the same `<base>` hold BASELINED status simultaneously. | BLOCKING |
| BL4 | Every SUPERSEDED specification has SUPERSEDED status confirmed. **Legacy spec:** `**Superseded By:**` header field must be non-empty. **STD spec:** YAML `status:` must be `SUPERSEDED`. Lineage is recorded in the lifecycle registry Event Log for both types. | BLOCKING |
| BL5 | Every evolved specification (carrying `**Supersedes:**`) points to a readable SUPERSEDED artifact. Verified at BASELINE time for the evolved version. | BLOCKING |
| BL6 | Every REOPEN event in the lifecycle registry has `reopen_date`, `actor`, and `reason` fields populated. | BLOCKING |
| BL7 | After a REOPEN, the specification exists at its draft path with DRAFT status. **Legacy spec:** `**Status:**` field is `DRAFT`. **STD spec:** YAML `status:` is `DRAFT`. | BLOCKING |
